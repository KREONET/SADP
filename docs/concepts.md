# SADP 기본 개념과 용어

Kubernetes를 조금 사용해 봤거나 SADP를 처음 접하는 사람을 위한 안내입니다.
구성요소 이름을 모두 외우기보다 **어떤 일을 맡는지**, **내가 어디까지 해야 하는지**를 먼저 이해하세요.

## SADP에서 사람이 하는 일

사용자는 Portal 웹 화면에서 앱을 신청합니다. 개발자는 실행할 프로그램과 배포 입력을 준비합니다.
관리자는 서버 환경과 외부 로그인 연결을 준비하고, 신청을 검토하며, 장애와 백업을 관리합니다.
한 사람이 여러 역할을 맡을 수도 있습니다.

SADP는 기존 RKE2 위에 서비스를 설치합니다. 운영체제 설치, RKE2 신규 설치, 조직의 로그인 서버
설정은 각각 담당자가 먼저 준비해야 합니다. 기존 RKE2의 버전 업데이트는 별도 운영 절차가 있습니다.

## 어느 서버에서 작업하나요?

| 표현 | 쉬운 설명 | 이곳에서 하는 일 |
| --- | --- | --- |
| 관리 워크스테이션 | 관리자가 코드를 검토하는 PC나 작업 서버 | 설정 생성, 변경 비교, 저장소 시험 |
| control-plane / server | Kubernetes 클러스터를 관리하는 서버 | 전체 설치, 클러스터 검사, 백업·복구 |
| worker / agent | 앱을 실행하는 서버 | 자기 서버의 네트워크 설정과 RKE2 agent 관리 |
| Squid 담당 노드 | 외부 HTTP(S) 통신을 중계하는 서버 | 프록시 설치, 허용 주소와 연결 상태 확인 |

워크스테이션과 control-plane을 같은 서버로 사용할 수 있습니다. Squid 담당 서버도 사이트 설정으로
정합니다. 실행 위치를 구분하는 이유는 명령이 **실행한 서버 자체**를 바꿀 수 있기 때문입니다.

`single`은 서버 한 대가 관리 기능과 앱 실행을 모두 맡습니다.
`multi`는 관리 서버 한 대와 worker 한 대 이상을 사용합니다.
두 구성 모두 관리 서버는 한 대이므로, 관리 서버 장애에 대비한 고가용성(HA) 구성은 아닙니다.

## 앱과 배포를 이해하는 용어

| 용어 | 뜻과 사용 예 |
| --- | --- |
| 클러스터 / 노드(Node) | Kubernetes로 함께 관리하는 서버들의 묶음 / 참여하는 서버 한 대 |
| 이미지(image) | 프로그램과 실행 환경을 묶은 배포물. 이미지로 컨테이너를 실행합니다. |
| Registry | 이미지를 저장하고 내려받는 저장소. Git 소스 저장소와 용도가 다릅니다. |
| tag / digest | 이미지 버전을 가리키는 이름 / 이미지 내용을 식별하는 해시. 내용이 바뀌지 않는 참조를 사용합니다. |
| Pod | Kubernetes에서 컨테이너를 실행하는 단위. 실행 중이어도 앱이 준비된 것은 아닐 수 있습니다. |
| Deployment / replica | 원하는 개수의 Pod를 유지하는 설정 / 같은 앱의 복제본 수. `0`이면 중지 상태입니다. |
| Service | Pod가 교체돼도 다른 앱이 일정한 이름과 포트로 접근하게 해 주는 내부 접속점 |
| Namespace | 리소스를 묶는 작업 영역. AppGroup은 여러 앱이 하나의 Namespace를 공유합니다. |
| AppGroup | Compose 등으로 여러 서비스를 함께 신청하는 묶음. 그룹 이름은 플랫폼 전체에서 유일해야 합니다. |
| preset / quota | 선택할 수 있는 CPU·메모리 묶음 / 사용할 수 있는 자원 상한 |
| PVC / StorageClass | 앱의 영속 저장공간 요청 / 그 저장공간을 제공하는 방식. Pod 재시작과 PVC 삭제는 다릅니다. |

웹 앱에는 프로그램이 실제로 듣는 `container port`를 입력합니다.
외부 HTTPS의 443 포트와 앱 컨테이너 내부의 포트가 꼭 같을 필요는 없습니다.
포트가 없는 AppGroup 서비스는 외부 웹 주소 없이 작업을 실행하는 **worker 서비스**입니다.
이때의 worker는 서버 역할을 뜻하는 worker 노드와 다른 의미입니다.
Portal 자체는 여러 프로세스가 겹쳐 실행되면 안 되므로 replica를 `0` 또는 `1`만 사용합니다.

## 접속과 통신을 이해하는 용어

사용자의 앱 접속은 대체로 다음 경로를 따릅니다. OIDC를 선택한 앱은 조직 로그인을 요구합니다.

```mermaid
flowchart LR
    Browser["브라우저: 앱 주소"] --> Gateway["Envoy Gateway: 외부 진입점"]
    Gateway --> Route["HTTPRoute: 주소별 연결 규칙"]
    Route --> Service["Service: 내부 접속점"]
    Service --> Pod["Pod: 실제 앱"]
```

| 용어 | 쉬운 설명 |
| --- | --- |
| DNS / FQDN | 이름을 IP로 찾는 기능 / 전체 도메인 이름 |
| NIC / interface | 서버의 네트워크 연결 장치 / 운영체제가 사용하는 장치 이름 |
| CIDR | IP 주소 범위를 적는 방식. `<IPv4>/32`는 IPv4 주소 하나를 뜻합니다. |
| NAT / direct | 경계 장비가 공인 접속을 내부로 전달하는 방식 / 공인 IP를 가진 노드로 직접 접속하는 방식 |
| Gateway / HTTPRoute | 외부 요청을 받는 진입점 / 도메인과 경로에 맞춰 앱으로 보내는 규칙 |
| ingress / egress | 앱으로 들어오는 연결 / 앱이 밖으로 새로 만드는 연결 |
| NetworkPolicy | Pod의 연결을 허용하거나 제한하는 규칙. 사용자별 데이터 권한까지 검사하지는 않습니다. |
| default-deny | 기본적으로 연결을 차단하고 필요한 연결만 허용하는 방식 |
| Squid / proxy | 승인된 외부 HTTP(S) 요청을 중계하는 프로그램 / 이런 중계 기능 |
| CoreDNS | 클러스터 안에서 서비스 이름과 외부 도메인을 해석하는 DNS 서비스 |

외부 공개와 외부 통신은 별개입니다. `external` 앱이라도 외부 API 호출은 egress 정책과 실제
네트워크 경로가 허용해야 가능합니다. `web`은 내부 대역을 제외한 TCP 80/443 허용이며,
특정 도메인만 허용하는 기능이 아닙니다.

## 로그인과 비밀값을 이해하는 용어

| 용어 | 쉬운 설명 |
| --- | --- |
| SSO / IdP | 조직 계정으로 로그인하는 방식 / 그 로그인을 제공하는 외부 서버 |
| OIDC | SADP가 외부 로그인 서버와 신원 정보를 주고받는 규격 |
| SAML / broker | 다른 인증 규격 / SAML 인증을 받아 SADP에 OIDC로 전달하는 외부 중계 서버 |
| issuer / discovery | 로그인 정보를 발급하는 주체의 정확한 주소 / 인증 endpoint를 알려 주는 문서 |
| client ID / client secret | 로그인 서버에 등록한 앱의 식별자 / 그 앱의 비밀값. 사용자의 비밀번호와 다릅니다. |
| callback / redirect URI | 외부 로그인 뒤 앱으로 돌아오는 주소. IdP에 등록한 주소와 정확히 맞아야 합니다. |
| claim / role | 인증 결과에 담긴 사용자·그룹 정보 / 작업을 허용하는 역할 |
| Secret / ConfigMap | 비밀번호·토큰 같은 민감한 설정 / 공개돼도 되는 일반 설정 |
| OpenBao | Secret 실제 값을 보관하고 접근을 제한하는 저장소 |
| ESO / ExternalSecret | OpenBao 값을 Kubernetes로 공급하는 도구 / 가져올 값의 이름과 경로를 선언하는 리소스 |
| SecretStore / ClusterSecretStore | ESO가 비밀 저장소에 접속하는 설정. 각각 Namespace 범위 / 클러스터 범위 리소스입니다. |
| sealed / unseal | OpenBao가 잠겨 Secret을 제공할 수 없는 상태 / 복구 재료로 잠금을 푸는 작업 |
| Reloader | 설정 또는 Secret 변경을 감지해 사용하는 워크로드가 다시 읽도록 돕는 도구 |

로그인에 성공했다고 모든 데이터에 접근할 권한이 생기지는 않습니다.
다른 사람의 파일을 내려받을 수 있는지는 **앱 서버가 따로 검사**해야 합니다.
자세한 책임 범위는 [보안 보장과 한계](security-boundaries.md)를 읽으세요.

## 설정 파일과 GitOps를 이해하는 용어

`site.env`는 사이트 주소·노드·네트워크 등 입력을 모아 둔 파일입니다.
생성기는 이 입력으로 **계약(contract)**, 즉 플랫폼 설정의 기준 파일을 만들고 하위 YAML을 생성합니다.
`SSOT`는 서로 다른 파일을 따로 고치지 않도록 기준을 한 곳에 둔다는 뜻입니다.

```text
사용 중인 site.env 수정
  → render: 계약과 설정 파일 생성
  → diff: 변경 내용 확인
  → test: 저장소 시험
  → commit/push: 검토한 변경을 Git에 기록·전송
  → GitOps 동기화와 필요한 node/cluster 적용
  → 실제 상태 검수
```

| 용어 | 쉬운 설명 |
| --- | --- |
| render / 생성물 | 입력으로 설정 파일을 만드는 작업 / 그 결과 파일. 생성물을 손으로 고치지 않습니다. |
| Helm / Chart / values | Kubernetes 설정을 만드는 도구 / 설정 템플릿 묶음 / 템플릿에 넣을 입력값 |
| GitOps / Argo CD | Git에 기록한 설정을 배포 기준으로 쓰는 방식 / Git과 클러스터를 동기화하는 도구 |
| Forgejo / PR | Git 저장소를 운영하는 서비스 / 병합 전에 검토하는 변경안(Pull Request) |
| revision / commit | 특정 소스·설정 상태를 가리키는 버전 / Git에 저장한 변경 기록 |
| drift / reconcile | 기준 설정과 실제 상태의 차이 / 실제 상태를 기준에 맞추는 작업 |
| preflight / acceptance | 적용 전에 필요한 조건 확인 / 설치 후 서비스의 동작과 경계 검수 |
| runbook | 장애 복구나 유지보수 때 따르는 작업 절차서 |

Argo CD는 GitOps 리소스를 동기화합니다. 서버의 방화벽·RKE2 설정까지 모든 변경을 대신 적용하는
도구는 아니므로, 변경 범위에 따라 node 또는 cluster 단계도 실행합니다.

## 상태와 유지보수 용어

| 표시 또는 용어 | 어떻게 읽나요? |
| --- | --- |
| `Running` / `Ready` | 프로세스가 실행 중 / 요청을 처리할 준비가 됨. 실행 중이어도 준비 상태가 아닐 수 있습니다. |
| `Synced` / `Healthy` | Argo가 비교한 Git 설정과 일치 / 리소스 상태가 정상. 적용하려던 revision도 함께 확인합니다. |
| `Accepted` / `Programmed` | Gateway가 설정을 수락 / 트래픽 처리 구성이 반영됨. 앱 기능까지 검증되지는 않습니다. |
| cordon / drain / uncordon | 새 Pod 배치를 막기 / 기존 Pod를 안전하게 비우기 / 새 배치를 다시 허용하기 |
| snapshot / checksum | 특정 시점의 백업 / 파일 손상을 확인하는 해시. checksum 성공과 복원 성공은 별개입니다. |
| RPO / RTO | 허용할 수 있는 데이터 손실 시간 / 서비스 복구에 허용하는 시간 |
| `[OK]` / `[WARN]` / `[SKIP]` | 해당 검사 성공 / 확인할 경고 / 이유를 표시하고 생략. 생략은 성공이 아닙니다. |
| `[FAIL]` / `[CAUSE]` / `[NEXT]` | 검사 실패 / 분류된 원인 / 다음에 확인할 명령 |

실제 작업을 시작하려면 [문서 홈](README.md)에서 자신의 역할에 맞는 가이드를 고르세요.
