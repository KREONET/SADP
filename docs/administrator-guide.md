# SADP 관리자 가이드

> 문서 경로: [문서 홈](README.md) → 관리자 가이드
> 대상: 플랫폼 설치·운영·보안·GitOps·장애 대응 담당자

이 문서는 관리자가 무엇을 소유하고 어떤 순서로 판단해야 하는지 설명합니다. 새 환경을 실제로
설치할 때는 [설치 가이드](installation.md), 개별 장애를 처리할 때는 해당 Runbook을 사용합니다.

## 1. 관리자 책임 범위

| 영역 | 관리자가 소유 | 앱 개발자가 소유 |
| --- | --- | --- |
| 클러스터 | RKE2 상태, StorageClass, CNI, 노드 유지보수 | Pod가 요구하는 일반 자원 |
| 네트워크 | NIC 역할, Gateway, NAT/direct, DNS, Squid, NMS | 앱의 필요한 port와 목적지 |
| 인증 | Keycloak realm/client/group, 상위 IdP | 앱 callback 요구사항 |
| Secret | OpenBao/ESO/Reloader, 권한 경계 | 앱별 key 이름과 값 입력 |
| GitOps | Forgejo bot, Argo repository/Application, 승인 정책 | 소스 코드와 배포 요청 |
| Registry | push/pull credential 분리, 노드 접근 | Dockerfile과 immutable image |
| 복구 | 백업 검증, 승인된 복원 | 앱 데이터 복구 요구사항 |

이 저장소는 OS와 RKE2 자체를 설치하지 않습니다. 3노드 RKE2가 이미 Ready인 상태를 입력으로 받습니다.

## 2. 관리자가 매일 보는 것

### 기본 상태

```bash
kubectl get nodes -o wide
kubectl get applications -n devtroncd
kubectl get gateway,httproute -A
kubectl get externalsecret,secretstore,clustersecretstore -A
kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
```

### SADP acceptance

control-plane 노드에서 실행합니다.

```bash
sudo bash ./sadp --verify-portal-auth
sudo bash ./sadp --verify-testbed
```

`verify-testbed`의 호스트 검사는 실행한 control-plane 한 대만 검사합니다. worker 전체를 검사했다고
기록하지 않습니다.

### 점검 결과 기록

다음만 기록합니다.

- 실행 시각과 대상 cluster/site
- Git revision
- 성공/실패한 검사 이름
- Kubernetes resource 이름과 상태
- 다음 담당자와 조치 기한

Secret 값, token, session cookie, 인증서 private key는 기록하지 않습니다.

## 3. 설정과 변경의 소유권

### 사이트 설정

실제 사이트 입력은 Git 밖의 `/etc/sadp/site.env`가 소유합니다.

```text
site.env
  → configure-site.py
  → 플랫폼 계약
  → 생성된 apps/argocd/platform/rke 파일
  → 검토된 Git commit
  → Argo CD
```

- `site.env`가 있으면 계약을 먼저 직접 고치지 않습니다.
- `# Generated by` 파일은 직접 수정하지 않습니다.
- `render --apply` 후 반드시 diff를 검토하고 commit/push합니다.
- 클러스터를 먼저 긴급 변경했다면 `site.env`에도 같은 사실을 반영하지 않는 한 다음 렌더에서 되돌아갑니다.

전체 입력 규칙은 [사이트 설정 참조](site-configuration.md)를 사용합니다.

### Secret

| 종류 | 위치 |
| --- | --- |
| Secret 이름·remote path·property | Git 계약/values |
| 실제 애플리케이션 값 | OpenBao KV v2 |
| Pod 런타임 Secret | ESO가 만든 Kubernetes Secret |
| 설치 bootstrap 자격증명 | `/etc/sadp/secrets/`의 root 전용 파일 |

통합 설치기는 bootstrap 파일이 일반 파일이고 root 소유이며 mode `0400` 또는 `0600`인지 확인합니다.
파일 내용을 출력하거나 `site.env`에 복사하지 않습니다.

### 노드 설정

노드 변경은 계획 → 적용 → 수동 재시작 순서입니다.

```bash
sudo bash ./sadp --install --env-file /etc/sadp/site.env --phase node
sudo bash ./sadp --install --env-file /etc/sadp/site.env --phase node --apply
```

설치기는 RKE2를 자동 재시작하지 않습니다. drain과 서비스 재시작, Ready 확인은 유지보수 창에서
한 대씩 수행합니다.

## 4. 새 사이트와 변경 배포

### 새 사이트

[설치 가이드](installation.md)의 다음 경계를 지킵니다.

```text
render
  → diff 검토
  → commit/push
  → 각 노드 node 적용
  → 수동 재시작/Ready
  → control-plane cluster 적용
```

`all --apply`는 허용되지 않습니다. 노드 재시작 확인을 건너뛴 채 cluster 단계로 넘어가는 것을
막기 위한 설계입니다.

### 기존 사이트 설정 변경

1. 영향 범위를 분류합니다: GitOps-only / 노드 변경 / Secret 변경 / 데이터 변경.
2. `/etc/sadp/site.env`를 수정합니다.
3. `render` 계획을 확인합니다.
4. 생성물을 작성하고 diff를 검토합니다.
5. `bash ./sadp --test`를 통과시킵니다.
6. commit/push 후 Argo sync 상태를 확인합니다.
7. 노드 영향이 있을 때만 유지보수 창에서 `node --apply`를 수행합니다.
8. acceptance 결과를 기록합니다.

### TLS 단계 값

다음 값은 단순 설정이 아니라 완료된 운영 단계의 기록입니다.

| 단계 | 값 |
| --- | --- |
| staging 인증서 검증 완료 | `ACME_STAGING_VERIFIED=true` |
| production issuer 사용 | `TLS_ISSUER_MODE=production` |
| 운영 wildcard Secret Ready | `EXISTING_GATEWAY_TLS_READY=true` |

클러스터 상태보다 `site.env`가 뒤처지면 다음 렌더가 HTTPS 경로를 과거 상태로 되돌릴 수 있습니다.
발급 절차는 [DNS-01 Runbook](letsencrypt-dns01.md)을 따릅니다.

## 5. 계정과 권한 운영

### 사용자 권한

- 일반 사용자는 kubeconfig, OpenBao root token, RKE2 token이 필요하지 않습니다.
- Portal 조회와 배포 권한은 Keycloak client role로 나눕니다.
- 앱 Secret 권한은 앱별 group/role로 제한합니다.
- `developer`나 `app-admin`이라는 이름만으로 모든 앱 Secret을 열지 않습니다.
- `platform-admin`은 일상 사용자 계정과 분리하고 최소 인원에게만 부여합니다.

### Forgejo와 Registry

다음 credential을 하나로 재사용하지 않습니다.

| credential | 최소 권한 |
| --- | --- |
| Argo repository | Git read |
| Portal Forgejo bot | 승인된 repository PR 생성/병합 |
| Registry push | 지정 project push |
| Kubernetes pull | 지정 project pull |

회전 절차는 [Forgejo token 회전 Runbook](runbooks/forgejo-token-rotation.md)을 사용합니다.

### 외부 Keycloak/IdP

외부 Keycloak을 사용할 때도 공개 issuer와 callback은 계약의 SSO host를 유지합니다. 외부 VM의
내부 주소를 브라우저 issuer로 노출하지 않습니다. SAML IdP 연결과 계정 연결 문제는
[외부 Keycloak Runbook](keycloak-external.md)을 사용합니다.

## 6. 장애 분류

| 증상 | 첫 확인 | Runbook/다음 단계 |
| --- | --- | --- |
| 모든 공개 URL 연결 거부 | `PUBLIC_EXPOSURE_MODE`, 공인 IP 소유, Gateway | [네트워크](network-egress.md) |
| HTTP는 되지만 HTTPS 실패 | Certificate/Secret/Gateway listener | [DNS-01](letsencrypt-dns01.md) |
| `invalid_saml_response` + `Assertion expired` | Audience 선행 로그, 양쪽 NTP/UTC 차이, Assertion 시간·ID 재사용 | [외부 Keycloak](keycloak-external.md#34-invalidsamlresponse--audience-오류와-실제-만료를-로그로-분리) |
| 앱 하나만 `ImagePullBackOff` | image tag, pull Secret, Registry 권한 | Pod event와 Registry pull credential |
| ExternalSecret `Ready=False` | SecretStore, SA, OpenBao role/path | ESO event를 값 없이 기록 |
| Worker만 외부 image/DNS 실패 | containerd proxy, CoreDNS upstream, Squid | [네트워크](network-egress.md) |
| NMS 앱만 실패 | mode, allowed app, CIDR/port, 전용 route | [네트워크 NMS 절](network-egress.md#9-nms-mode) |
| Portal 배포 API 503 | Forgejo env/token/연결 | [Portal API](portal-api.md) |
| 데이터 손상·etcd/OpenBao/PostgreSQL 장애 | 추가 쓰기 중단 | [복구](recovery.md) |

긴급하게 클러스터 리소스를 직접 고쳤다면 임시 조치, 원인, Git/계약 반영 여부를 함께 기록합니다.
Argo가 되돌리기 전에 SSOT를 수정하거나 승인된 sync 중지 절차를 사용합니다.

## 7. 정기 운영 체크리스트

### 매일

- [ ] Node와 핵심 Application이 Healthy/Ready다.
- [ ] 실패 Pod와 반복 restart가 없다.
- [ ] Gateway와 주요 HTTPRoute가 Accepted다.
- [ ] ExternalSecret 실패가 없다.

### 매주

- [ ] 백업이 생성되었고 checksum/형식 검증을 통과했다.
- [ ] 인증서 만료 기간이 기준 이상이다.
- [ ] Forgejo/Registry/Argo 실패와 비정상 로그인 기록을 검토했다.
- [ ] node disk와 PVC 사용량을 검토했다.

### 변경 전

- [ ] `site.env`와 checkout의 생성물이 동기화되어 있다.
- [ ] diff에 Secret이나 실제 Private 값이 없다.
- [ ] Helm을 포함한 `bash ./sadp --test`가 통과했다.
- [ ] 노드 영향과 롤백 지점을 정의했다.
- [ ] 데이터 변경이면 복원 가능한 백업을 확인했다.

### 변경 후

- [ ] Argo sync와 rollout이 완료되었다.
- [ ] public/OIDC/internal 동작이 계약과 일치한다.
- [ ] Portal 인증과 핵심 acceptance가 통과했다.
- [ ] 임시 credential, hosts 항목, debug 설정을 정리했다.
