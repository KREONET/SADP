# SADP 파생 프로젝트 보안 보완 이식 프롬프트

아래 내용을 대상 프로젝트의 AI 에이전트에게 그대로 전달한다.

---

이 저장소는 SADP 파생 프로젝트다. 저장소 전체와 `Other-Source`를 다시 비교하는 일반적인
리팩터링이 아니라, 아래 보안 경계와 운영 기능이 이 프로젝트에도 실제로 적용됐는지 감사하고
누락된 부분을 구현해라. 보고서만 작성하지 말고, 근거가 확인된 문제는 코드·Chart·스크립트·
문서·회귀시험까지 수정한 뒤 저장소의 전체 테스트를 실행해라.

먼저 루트와 작업 대상 하위 디렉터리의 `AGENTS.md`를 전부 읽고 따른다. `site.env` 존재 여부와
파일의 `Generated by` 헤더를 확인한다. 생성된 YAML을 직접 편집하지 말고 계약 또는 생성 로직을
수정한 뒤 다시 렌더링한다. 기존 사용자 변경은 보존하고 Secret, 실제 IP/FQDN, 저장소 URL,
사용자명, token, 인증서 또는 개인키를 출력하거나 커밋하지 않는다.

참조 구현은 SADP의 다음 파일이다. 대상 저장소의 디렉터리 구조와 이름이 다르면 역할이 같은
파일을 찾아 적용한다.

- `charts/app-profile/templates/httproute.yaml`
- `charts/app-profile/values.yaml`
- `charts/app-profile/values.schema.json`
- `scripts/ops/quarantine-app.sh`
- `scripts/verify/verify-testbed.sh`
- `scripts/tests/render-test.sh`
- `scripts/tests/quarantine-app-test.py`
- `docs/security-boundaries.md`
- `docs/network-egress.md`
- `docs/developer-guide.md`
- `docs/administrator-guide.md`
- `AGENTS.md`

핵심 전제는 다음과 같다.

> “Pod의 아웃바운드를 제한했으므로 앱을 안전한 블랙박스로 취급할 수 있다”는 주장은 틀리다.
> Kubernetes NetworkPolicy는 허용된 연결의 응답 트래픽을 허용한다. 침해된 앱은 자신이 읽을 수
> 있는 데이터를 정상 응답·오류·다운로드·redirect에 담을 수 있다. 사용자별 인가 오류, 데이터
> 변조와 삭제는 외부 연결 없이도 발생한다. Pod egress와 직원 브라우저의 통신도 별도 경계다.

다음 항목을 순서대로 처리한다.

1. 현재 보장과 과장된 표현 감사

- README, 운영 문서, 앱 등록 문서, 주석에서 egress 차단을 DLP, 데이터 유출 방지, 안전한 앱 실행,
  강한 테넌트 격리처럼 표현한 곳을 찾는다.
- 실제 구현을 근거로 플랫폼이 보장하는 것과 보장하지 않는 것을 구분한다.
- 최소 보장 문구는 “승인되지 않은 새 외부 연결을 제한한다”, “앱별 Secret과 플랫폼 권한을
  좁힌다”, “침해 의심 앱의 외부 경로와 실행 Pod를 격리할 수 있다”로 쓴다.
- 정상 응답·redirect를 통한 유출, 앱 내부의 사용자별 객체 인가, 자기 권한에 의한 변조·삭제,
  별도 백업이 없는 앱 PVC 복구, 단말 침해는 보장하지 않는다고 명시한다.

2. 일반 외부 앱의 브라우저 응답 경계

- Gateway API `HTTPRoute`를 사용한다면 `ResponseHeaderModifier`로 일반 외부 앱 응답에 다음을
  강제한다.
  - `Cache-Control: no-store`
  - 동일 origin 중심 CSP: `default-src`, `base-uri`, `object-src`, `frame-ancestors`, `form-action`,
    `connect-src`, `img-src`, `font-src`, `style-src`, `script-src`
  - `Cross-Origin-Resource-Policy: same-origin`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
  - `Referrer-Policy: no-referrer`
  - `X-Content-Type-Options: nosniff`
  - `X-Frame-Options: DENY`
- 프레임워크가 요청별 nonce CSP를 자체 생성하는 Portal에는 정적 CSP를 덮어쓰지 않는다. 이 예외는
  단순 앱 이름만으로 열지 말고 Portal 전용 pipeline/권한 불변식도 함께 만족할 때만 허용한다.
- 사용자 일반 앱이 values 변경으로 응답 보안 정책을 끌 수 없게 Chart 렌더에서 거부한다.
- 이 CSP도 서버 응답 본문, top-level redirect, 다운로드 자체를 막는 DLP가 아니라고 문서화한다.
- 이 프로젝트의 Gateway/controller가 `ResponseHeaderModifier`를 지원하는지 공식 문서와 실제
  `HTTPRoute Accepted=True`로 확인한다. 지원하지 않으면 조용히 생략하지 말고 동등한 Envoy 정책을
  구현하거나 명확히 실패시킨다.

3. 사용자별 데이터 인가 책임

- OIDC 그룹 또는 로그인 성공은 앱 진입 권한일 뿐 레코드·파일·프로젝트별 권한이 아님을 개발자
  가이드와 승인 체크리스트에 넣는다.
- 조회·수정·삭제뿐 아니라 목록, 검색, 내보내기, 다운로드 URL, WebSocket, 캐시 key에서도 서버가
  요청자와 객체 관계를 검사해야 한다고 명시한다.
- 플랫폼의 이미지/CVE/YAML 검사가 앱 비즈니스 로직의 인가를 자동 증명한다고 쓰지 않는다.
- 민감 데이터 앱은 사용자 A가 사용자 B의 객체를 읽거나 변경할 수 없는 negative test 또는 코드
  검토 증거가 없으면 승인하지 않는 운영 기준을 추가한다.

4. 침해 의심 앱 즉시 격리

- `--apply` 없이 상태와 계획만 출력하고 `--apply`에서만 변경하는 관리자 명령을 추가한다.
- 입력 app과 Namespace를 DNS label 규칙으로 검증한다.
- Argo Application 파일명을 추측하지 말고 destination Namespace와 Helm release name을 함께 조회해
  정확히 한 개일 때만 진행한다.
- 적용 순서는 child Argo reconcile 중지 → 외부 HTTPRoute 제거 → Deployment replicas 0 → 대상 Pod
  0과 Route 부재 확인이다. GitOps self-heal이 Route를 다시 만들면 성공으로 보고하지 않는다.
- Service, PVC, Secret, 신청·감사 기록은 증거와 복구를 위해 자동 삭제하지 않는다.
- 변경 전 Application 상태는 root 전용 상태 디렉터리에 mode 0600으로 저장하되 Secret 본문은
  수집하지 않는다.
- 복구는 격리 해제 버튼 하나로 만들지 않는다. 로그와 영향 범위 보존, 노출된 Secret 회전,
  알려진 정상 immutable image 준비, GitOps에 replicas 0과 exposure disabled 반영, 정확한 revision
  Synced 확인, 별도 승인된 재개 변경 순서를 문서화한다. 격리 전 이미지를 그대로 다시 켜지 않는다.

5. 기존 최소 권한 재검증

- 일반 앱의 ServiceAccount token 자동 마운트가 꺼져 있는지 확인한다.
- API 접근이 필요한 앱만 짧은 수명의 projected token과 고정된 namespaced Role을 쓰는지 확인한다.
- 컨테이너가 non-root, read-only root filesystem, privilege escalation 금지, capability 전체 제거,
  RuntimeDefault seccomp를 유지하는지 확인한다.
- 앱별 OpenBao/ESO path, role, ServiceAccount, Secret key가 다른 앱과 교차되지 않는지 확인한다.
- AppGroup을 강한 적대적 멀티테넌시 경계라고 표현하지 않는다. 같은 Namespace 안에서도 ingress와
  egress 양쪽에 선언된 앱 연결만 허용되는지 렌더 시험으로 확인한다.

6. 공통 Auth·패키지·빌드 안전장치도 함께 확인

- 회전형 OIDC/Keycloak refresh token을 사용하는 경우 같은 구 token의 동시 갱신을 프로세스 안에서
  한 번으로 병합한다. 진행 중 map이 가득 찼을 때 항목을 버리거나 추적하지 않은 두 번째 IdP 호출을
  시작하지 말고, 한 건 완료까지 기다린 뒤 key와 용량을 다시 검사한다. 실패 결과는 캐시하지 않는다.
- `versions.lock.yaml`, UI `package.json`, package manager lock의 실제 resolved 버전, Docker
  frontend/runtime 버전을 CI에서 함께 대조해 부분 업데이트를 거부한다.
- 원격 빌더에 보내는 tar와 Docker context에서 모든 깊이의 `.env`, `.env.*`, `.git`, local build
  output을 제외한다. 공개 `NEXT_PUBLIC_*`도 화이트리스트 파서로만 전달한다.
- IdP 설치·realm/client/user/group 관리 방식은 프로젝트별 소유권 경계가 다르므로 SADP의 외부
  OIDC 방식이나 다른 파생본의 Keycloak provisioner를 그대로 복사하지 않는다.

7. 반드시 추가할 회귀와 인수검사

- 일반 외부 앱 렌더에 응답 보안 헤더가 모두 존재한다.
- 일반 앱이 application-owned CSP 예외를 요청하면 렌더가 실패한다.
- Portal 렌더에는 Gateway 정적 CSP가 없고 자체 nonce CSP 시험이 계속 통과한다.
- 격리 명령은 잘못된 app/Namespace를 거부하고, destination+release로 대상을 하나만 고르며,
  plan에서는 변경하지 않는다.
- 격리 적용 코드의 순서가 reconcile 중지 → Route 제거 → scale 0 → Pod 0 확인이다.
- 클러스터 인수검사는 manifest 존재만 보지 않고 실제 일반 앱 HTTPS 응답에서 `no-store`, CSP의
  `connect-src 'self'`, CORP, `nosniff`를 확인한다.
- NetworkPolicy blocked/web/custom의 기존 정상·금지 profile 시험과 OIDC 허용 그룹 시험을 유지한다.
- Auth coordinator가 있다면 동시 같은 token, 회전 직후 구 token, 용량 포화, 실패 후 다른 대기자의
  진행, 다른 사용자 결과 분리를 시험한다.

8. 완료 보고 형식

완료 보고에는 다음을 구분해서 적는다.

- 실제로 수정한 취약점과 파일
- 플랫폼이 새로 보장하는 범위
- 여전히 보장하지 않는 범위
- 실행한 테스트와 통과 건수
- Helm/controller/Node 등 검증에 사용한 실제 버전
- 클러스터에서 확인하지 못한 항목
- 운영 적용 전에 필요한 render → diff → commit/push → cluster acceptance 순서

실제 클러스터 변경, Secret 회전, 앱 격리, 이미지 삭제 또는 배포는 명시적으로 요청받지 않았다면
실행하지 않는다. 로컬 코드와 검증 가능한 산출물까지 완성하고, 운영 명령은 plan 기본값으로 둔다.
